PART 1 - THE BIG PICTURE (What is a Scanner and why)
================================================================================

A compiler has a pipeline:

   Source File --> [READER/Buffer] --> [SCANNER] --> [Parser] --> [Code Gen]
                       (A2)              (A3=THIS)      (A4)         (A5)

- READER (A2): loads the source file into memory, gives characters one at a time.
- SCANNER (A3, THIS ASSIGNMENT): reads those characters and groups them into
  TOKENS (the "words" of the language).
- PARSER (A4, later): checks the token sequence follows the grammar.

One sentence:
  "The Scanner turns a stream of CHARACTERS into a stream of TOKENS."

Example (Scribe):
   Input chars:  w h o l e   x   =   4 2 ;
   Scanner tokens:
        KW_T(whole)  AVID_T(x)  ASS_T(=)  INL_T(42)  EOS_T(;)

================================================================================
PART 2 - THE SCRIBE LANGUAGE (our own DSL, distinct from the Sofia example)
================================================================================

Scribe uses its OWN keywords and symbols so it is not the professor's Sofia
sample:

   Method marker : name ends with  $      e.g. main$   print$
   Comment       : ~ ... ~                e.g. ~ this is a comment ~
   String        : " ... "                e.g. "Hello world!"

   Keywords:
     vault    (declarations block)   check   (if)
     logic    (statements block)     so      (then)
     whole    (integer type)         alt     (else)
     deci     (real type)            during  (while)
     text     (string type)          run     (do)
                                      giveback(return)

Sample Scribe program (input/hello.txt):
   ~ Scribe Hello World ~
   main$() {
       vault { whole x; text msg; }
       logic {
           x = 42;
           msg = "Hello world!";
           print$(msg);
           giveback;
       }
   }

PART 3 - HOW THE SCANNER WORKS (two-part hybrid strategy)
================================================================================

PART I  - TOKEN-DRIVEN (direct switch-case): single-character tokens
     ;  -> EOS_T        (  -> LPR_T    )  -> RPR_T    {  -> LBR_T    }  -> RBR_T
     =  -> ASS_T        + - * /  -> ART_T          < >  -> REL_T
     space/tab -> skipped     newline -> line++     \0 / 0xFF -> SEOF_T

PART II - TABLE-DRIVEN (DFA): multi-character tokens (identifiers, keywords,
     numbers, strings, comments) recognized by walking a TRANSITION TABLE.

Why hybrid? Simple symbols do not need a state machine; complex patterns do.

================================================================================
PART 4 - THE DFA (Transition Table)
================================================================================

Columns = character CLASS (9 of them), Rows = STATE (15 of them).

Character classes (columns):
   [A-z] letters | [0-9] digits | _ | $ | " (quote) | SEOF | ~ | . (period) | other

Key states:
   S0  : start
   S1  : reading letters/digits (identifier or keyword body)
   S2  : accept - Method name (ended with $)      -> funcID  => MNID_T
   S3  : accept - Keyword OR variable identifier  -> funcID  => KW_T / AVID_T
   S4  : reading inside a string  "..."
   S5  : accept - String literal                  -> funcSL  => STR_T
   S6  : reading inside a comment ~...~
   S7  : accept - Comment                         -> funcCMT => CMT_T
   S8  : accept - Error (no retract)              -> funcErr => ERR_T
   S9  : accept - Error (with retract)            -> funcErr => ERR_T
   S10 : reading an integer (digits)
   S11 : seen a '.' (need a fraction digit)
   S12 : reading the fraction of a float
   S13 : accept - Integer literal                 -> funcIL  => INL_T
   S14 : accept - Floating-point literal          -> funcFPL => FPL_T

Support tables:
   - stateType[]       : NOT-accepting / accept-no-retract / accept-with-retract
   - finalStateTable[] : FUNCTION POINTERS - which function to call at a final state

"Retract" = put one char back (we read one past the end of the token).

================================================================================
PART 5 - THE ACCEPTING FUNCTIONS
================================================================================

   funcID  -> if lexeme ends with '$' => MNID_T (method name);
              else look up keyword table: match => KW_T, no match => AVID_T
   funcIL  -> integer literal token (validates it fits in a short int) => INL_T
   funcFPL -> floating-point literal token (range checked)             => FPL_T
   funcSL  -> stores string in the String Literal Table                => STR_T
   funcCMT -> comment token, counts newlines for line tracking         => CMT_T
   funcErr -> error token (truncates long errors to ERR_LEN-3 + "...") => ERR_T

Keyword table (Scribe): vault, logic, whole, deci, text, check, so, alt,
                        during, run, giveback

PART 6 - WHAT WAS CODED / DONE IN THIS ASSIGNMENT
================================================================================

STEP 1 - Reuse previous assignments
   - Brought in A1 (Coder - Vigenere cipher) and A2 (Reader/Buffer).
   - Scanner reads the ENCRYPTED source; readerLoad() DECRYPTS it into the buffer.

STEP 2 - Define OUR language (Scribe), distinct from the Sofia sample
   - Own keywords (vault, logic, whole, ...), own symbols ($ method, ~ comments,
     " strings). Datatype prefixes: scribe_intg, scribe_char, scribe_strg, ...

STEP 3 - Wire the Scanner into the driver
   - Compilers.c: option '3' (PGM_SCN) calls main3Scanner() -> starts the scanner.

STEP 4 - Token definitions (Step3Scanner.h)
   - enum TOKENS: ERR_T, MNID_T, INL_T, STR_T, LPR_T, RPR_T, LBR_T, RBR_T,
                  KW_T, EOS_T, RTE_T, SEOF_T, CMT_T, AVID_T, FPL_T,
                  ASS_T, ART_T, REL_T
   - Transition table (15x9), stateType[], finalStateTable[], keywordTable[].

STEP 5 - Scanner engine (Step3Scanner.c)
   - startScanner(), tokenizer() (Part I switch + Part II DFA), nextClass(),
     nextState(), the accept functions, printToken(), printScannerData().

STEP 6 - Main driver (Main3Scanner.c)
   - Loads+decrypts source, creates the String Literal Table, loops tokenizer()
     + printToken() until SEOF_T, then prints the string table and statistics.

STEP 7 - Extended the scanner (the A3 development work)
   - Added variable identifiers (AVID_T), integer literals (INL_T),
     floating-point literals (FPL_T), and operators (ASS_T, ART_T, REL_T).
   - Extended the transition table from 10x8 to 15x9 (added a '.' column and
     integer/float states). The provided starter only handled "Hello World".

PART 8 - WHAT THE OUTPUT SHOWS (talking points)
================================================================================

For hello.scr the scanner produces (0 errors):
   CMT_T                        <- the ~ comment ~
   MNID_T  main$                <- method name (ends with $)
   LPR_T RPR_T LBR_T            <- ( ) {
   KW_T    vault / whole / ...  <- keywords
   AVID_T  x / msg              <- variable identifiers
   ASS_T                        <- assignment =
   INL_T   42                   <- integer literal
   STR_T   Hello world!         <- string literal (stored in string table)
   EOS_T                        <- semicolons
   ... and a token histogram at the end.

Talking points:
   - "Scribe is my own DSL: own keywords (vault/logic/whole...) and symbols
      ($ methods, ~ comments, " strings) - not the Sofia sample."
   - "The scanner is table-driven: adding a token means editing the transition
      table, not rewriting logic."
   - "Function pointers (finalStateTable) decide which accept function runs -
      the C way of doing polymorphic dispatch."
   - "It reuses A1 (decryption) and A2 (buffer) - the compiler pipeline."
   - "Defensive programming: illegal chars, unterminated strings/comments, and
      over-long lexemes are all handled without crashing."

================================================================================
PART 9 - KEY CONCEPTS TO MENTION
================================================================================

- Regular Expressions -> Transition Diagram -> Transition Table -> Code
- DFA (Deterministic Finite Automaton): one state, one transition per input
- Character classes = a reduced alphabet (equivalence classes of characters)
- Token vs Lexeme: lexeme = actual text ("whole"); token = its class (KW_T)
- Function pointers for accept-state dispatch
- Retract: putting back the extra char that signaled the token's end
- String Literal Table: strings stored separately, tokens hold an offset
- Line tracking for error reporting
